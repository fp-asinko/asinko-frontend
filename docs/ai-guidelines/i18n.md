# Internacionalización (i18n)

> El sitio es multi-idioma con [`next-intl`](https://next-intl.dev/). **Ningún texto visible al usuario se escribe directo en un componente.**

## Idiomas

| Locale | Rol                                         |
| ------ | ------------------------------------------- |
| `en`   | Idioma por defecto (y `x-default` para SEO) |
| `es`   | Secundario                                  |
| `pt`   | Secundario. **Portugués de Brasil**         |

Se usan códigos de idioma sin región (`pt`, no `pt-BR`) mientras haya una sola variante por idioma:

- `hreflang="pt"` alcanza a todos los hablantes de portugués, no solo Brasil.
- `Intl` (y por lo tanto `useFormatter`) ya aplica convenciones brasileñas para `pt`: fechas `30/09/2026`, números `1.234,56`.
- Las traducciones se escriben en **portugués brasileño** (vocabulario, "você", ortografía de Brasil).

Si en el futuro se suma portugués de Portugal, se migra a `pt-BR` / `pt-PT` con redirects 301 desde `/pt/...`.

Agregar un idioma = agregarlo en `src/i18n/routing.ts` + crear su archivo en `messages/` con **todas** las claves.

## Estructura

```
messages/
├── en.json            # Idioma por defecto: fuente de todas las claves
├── es.json
└── pt.json
src/
├── app/
│   └── [locale]/          # Todas las rutas cuelgan del locale
│       ├── layout.tsx
│       └── page.tsx
├── i18n/
│   ├── routing.ts         # locales, defaultLocale, pathnames
│   ├── navigation.ts      # Link, redirect, useRouter localizados
│   └── request.ts         # Config por request
└── proxy.ts               # Detección y redirección de locale (antes middleware.ts)
```

La configuración exacta de cada archivo sigue la [guía oficial de next-intl](https://next-intl.dev/docs/getting-started/app-router/with-i18n-routing) para la versión instalada.

## URLs

- **Todas las URLs llevan prefijo de idioma**: `/en/...`, `/es/...`, `/pt/...`. La raíz `/` redirige **siempre a `/en`** (inglés primero, `localeDetection: false`): no se mira el idioma del navegador. El usuario cambia de idioma desde el menú "⋯" de la barra superior (`MoreMenu`, `specs/header-refresh`), que conserva la página y los filtros.
- **Rutas traducidas** con `pathnames` en `routing.ts`: `/en/products`, `/es/productos` y `/pt/produtos`, no `/es/products`. Mejor para SEO y para el usuario.
- **Excepción: las páginas de comunidad, activo y perfil** (`/hub/{slug}`, `/asset/{symbol}`, `/user/{username}`) son iguales en todos los idiomas, con el prefijo: `/es/hub/macro`. Las fija el documento de requerimientos del PO y el design system linkea las menciones así (`specs/community-pages` CP-01). Como no se traducen, no van en `pathnames`.
- **Slugs de contenido** traducidos cuando el contenido lo está.
- Navegación siempre con `Link` / `useRouter` de `@/i18n/navigation`, **nunca** los de `next/link` o `next/navigation` (pierden el locale). Lo controla ESLint (ver `tooling.md`).

## Mensajes

**Namespaces por feature o sección**, igual que la estructura del código. `en.json` es la fuente: toda clave nueva se crea primero ahí.

```jsonc
// messages/en.json
{
  "common": { "actions": { "save": "Save", "cancel": "Cancel" } },
  "quote": {
    "form": {
      "title": "Request a quote",
      "email": { "label": "Email", "error": "Enter a valid email" },
    },
  },
}
```

- **Claves semánticas en inglés** (`quote.form.title`), no el texto en español como clave.
- **Nada de concatenar strings**: usar interpolación y plurales de ICU.

```tsx
// ❌ Se rompe en otros idiomas (orden de palabras, plurales)
<p>{t('cart.youHave')} {count} {t('cart.items')}</p>

// ✅ ICU: "{count, plural, =0 {Your cart is empty} one {# item} other {# items}}"
<p>{t('cart.summary', { count })}</p>
```

- **Rich text** con `t.rich()` en vez de partir el mensaje para meter un `<strong>` o un link.
- **Fechas, números y monedas** con `useFormatter` / `getFormatter`, nunca con `toLocaleString` a mano.

## Server y Client Components

- En Server Components: `getTranslations` / `getFormatter`.
- En Client Components: `useTranslations` / `useFormatter`. Pasar al cliente **solo los namespaces que necesita**, no todos los mensajes. La lista vive en `src/i18n/client-messages.ts` (`CLIENT_NAMESPACES`) y el layout pasa solo esos; un test recorre los archivos `'use client'` y falla si alguno usa un namespace que no está en la lista.
- **`app/[locale]/layout.tsx` es el layout raíz** (no hay `app/layout.tsx`): así `next/root-params` lee el idioma desde cualquier código de servidor (`i18n/request.ts`).
- **Rendering dinámico**: la CSP lleva un nonce por request (ver `security.md`), y Next.js solo lo aplica en render dinámico. Por eso no se usa `generateStaticParams` para pre-renderizar. Una página que pueda ser estática (legales, landing) se evalúa en su spec.

### 404

- `app/[locale]/[...rest]/page.tsx` llama a `notFound()` para toda URL inexistente dentro de un idioma, y se muestra `app/[locale]/not-found.tsx` (traducido, con el shell).
- **Las vistas van dentro del grupo `app/[locale]/(main)/`** junto con su `loading.tsx`. Un `loading.tsx` directamente en `[locale]/` envolvería al catch-all, la respuesta empezaría a enviarse como 200 y el 404 sería "blando".
- **Excepción: una vista que redirige o da 404 según los datos** (las páginas de comunidad, `specs/community-pages`) va **fuera** de `(main)` y **sin** `loading.tsx`: resuelve el dato antes de enviar nada, así la redirección es un 308 real y el 404 también. Lo que tarda (el feed) se transmite adentro, con su propio `Suspense`.
- Limitación conocida: con un layout raíz dinámico, el HTML inicial del 404 es el documento de error de Next y la página se dibuja en el cliente (status 404 y `noindex` correctos). Ver `specs/foundation/design.md § 10`.

## Esquemas de validación

Los mensajes de error de zod también se traducen: el esquema devuelve **claves**, y el componente las traduce.

```ts
// quote-form.schema.ts
email: z.email({ message: 'quote.form.email.error' })
```

## SEO multi-idioma

Ver `seo.md`:

- `hreflang` para cada idioma + `x-default` en todas las páginas.
- Canonical apuntando a la versión del **mismo** idioma (nunca todas al idioma por defecto).
- Metadata traducida en `generateMetadata` con `getTranslations`.
- `<html lang={locale}>` en el layout.
- Sitemap con las alternativas de idioma de cada URL.

## Testing

- Unitarios: envolver el componente con `NextIntlClientProvider` y los mensajes del idioma por defecto, con un helper `renderWithIntl` en `src/test/`.
- E2E: los flujos críticos corren en **todos los idiomas**.
- Un test en CI verifica que **todos los archivos de `messages/` tienen las mismas claves**. Una clave faltante rompe el build.

## Reglas para asistentes de IA

1. Todo texto nuevo va a `messages/` en **todos** los idiomas en el mismo cambio.
2. Si no hay traducción aprobada, se usa la del idioma por defecto y se marca con `TODO(i18n)` en el PR. Nunca inventar la traducción de copy de marketing.
3. No cambiar el texto de una clave existente sin revisar dónde se usa.
